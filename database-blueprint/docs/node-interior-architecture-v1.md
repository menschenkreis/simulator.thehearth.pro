# Node Interior Architecture V1

## Purpose

The top SVG map is the world skeleton. Each node interior has its own scene and interaction model.

The rebuild should not treat every node as the same kind of page.

Some interiors are visual SVG scenes. Some are generated application interfaces. Some are hybrid scenes with data-driven controls.

This document captures the prototype truth and the rebuild recommendation.

Important:

These interiors are concept drafts. They are allowed to improve.

The goal is not to copy the prototype pixel-for-pixel. The goal is to preserve what each node is trying to *do* and rebuild the interaction with better design, cleaner data, and safer architecture.

Preserve:

- metaphor
- purpose
- useful data shape
- learner interaction insight
- progress logic

Improve freely:

- layout
- visual polish
- responsiveness
- accessibility
- wiring
- data ownership
- route structure
- component boundaries

## Core Recommendation

Build nodes as routed scenes/components.

Do not keep the prototype pattern where every node writes HTML into `#p-foundation`.

Recommended:

- `/nodes/foundation` renders the Foundation pyramid and TeachingEngine lessons
- `/nodes/doing` renders the fretboard drill grid
- `/nodes/knowing` renders the bookshelf and reader
- `/nodes/practice` renders the temple/practice-session system
- `/nodes/study` renders the concept/term/study chamber
- `/nodes/create` renders the cauldron and creative workstation
- `/nodes/hearth` renders the brain/journey/reflection system
- `/nodes/mastery` renders the phoenix/inspiration chamber

## Node Interior Types

### Foundation

Interior type:

Hybrid scene plus TeachingEngine lessons.

Prototype:

Rainbow pyramid with seven blocks. Only the first complete lesson is fully wired.

Rebuild:

Keep the pyramid visual. Store smaller lesson units and TeachingEngine steps in data.

### Doing

Interior type:

Data-driven CSS grid.

Prototype:

Not an SVG. It is a 6-string by 8-level fretboard grid generated by JavaScript.

Important data:

- 6 string rows
- 8 levels
- drill-to-level mapping
- drill-to-string/category mapping
- progress state per drill

Rebuild:

Keep the fretboard metaphor, but move string rows, levels, drill placement, filters, and pass conditions into data.

### Knowing

Interior type:

Data-driven bookshelf and reader.

Prototype:

Not an SVG. It is an 8-level bookshelf carousel generated by JavaScript. Clicking a book opens a flipbook reader.

Important data:

- 8 reading levels
- books/categories per shelf
- topics per book
- progress by topic
- 50 percent unlock rule

Rebuild:

Keep the bookshelf scene, but use `book_sources`, `book_files`, `book_sections`, and `source_notes` rather than giant hardcoded topic objects.

### Practice

Interior type:

Guided session scene.

Prototype:

Temple/candle/metronome experience with local practice logs.

Rebuild:

Keep the temple and candle metaphor. Store session structure, drill links, timing, reflection prompts, and body checks in data.

### Study

Interior type:

Concept chamber and review system.

Prototype:

Shares Knowing content and auto-generates weak quizzes from HTML tags.

Rebuild:

Give Study its own role: reading music, terms, theory relationships, misunderstood-word recovery, quizzes, and source-note recall.

### Create

Interior type:

SVG scene plus data-driven prompt engine.

Prototype:

Uses cauldron illustration, ingredient toggles, obstructions, combos, and local text workspace.

The cauldron SVG is embedded as an image inside `.cauldron-vessel`; the prompt text floats over it in `#cauldronPrompt`.

The SVG itself is decorative. Interactivity is handled by HTML/CSS/JS:

- `.cauldron-ingredient`
- `.cauldron-ingredient.selected`
- `.cauldron-stir-btn`
- `.cauldron-bubbling`
- `cauldronMix()`

Rebuild:

Keep cauldron as scene. Store ingredients, obstructions, combos, saved seeds, and creative project notes as data.

Important vocabulary reconciliation:

The prototype Create node uses 8 ingredients: emotion, time, constraint, collaboration, cover, genre, acoustic, lyrical.

The newer obstruction/combo files use 5 creative elements: lyrics, melody, riff, rhythm, story.

Recommended model: keep both, but separate them into creative elements and obstruction modifiers.

### Hearth

Interior type:

SVG brain map plus live progress/reflection dashboard.

Prototype:

Brain map was built but never deployed because `scene-first.js` overrode `showHearth()`.

Rebuild:

Use the brain map as the Hearth scene, but make skill regions data-backed. Progress should be calculated from real student activity rather than scattered localStorage only.

### Mastery

Interior type:

Inspiration chamber.

Prototype:

Sparse content. Phoenix concept exists on the map, but interior is underdeveloped.

Rebuild:

Use Mastery for artists, advanced concepts, expression, performance, taste, and long-range direction.

## Panel Management Lesson

Prototype problem:

Most nodes render into `#p-foundation`, while Hearth has `#p-hearth`. This is confusing and made overwrites easier.

Rebuild recommendation:

Use proper routes/components and clear node-owned containers.

The frontend can still share layouts, but the app should not pretend every node is Foundation.

## Data Rules For Martin

Do not store giant render functions in the database.

Store:

- node identity
- scene type
- renderer key
- content source
- progress model
- action keys
- source links

Let the frontend render:

- fretboard grid
- bookshelf carousel
- brain SVG
- cauldron scene
- TeachingEngine lesson steps

## Prototype Blockers To Avoid

- `scene-first.js` overriding `showHearth`, `showPractice`, `showCreate`, etc.
- one shared panel for unrelated node scenes
- hardcoded drill levels
- hardcoded category-to-string mapping
- hardcoded bookshelf levels
- auto-generated quizzes from arbitrary HTML
- localStorage as the only source of truth
